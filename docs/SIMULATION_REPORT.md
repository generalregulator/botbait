## How the simulation works

The real server, session handlers, parser, IOC extractor, MITRE classifier, downloader, payload store, Telegram notifier (dedupe on) and AbuseIPDB reporter run in one process. Only the outside world is replaced: Telegram, AbuseIPDB and the malware host are local HTTP test servers. Traffic goes over real TCP sockets to all six listeners (ADB 5555, TR-069 7547, Telnet 23, Hikvision 80, TVT 81, Dahua 8080 as public labels), with the Android TV box persona on ADB and the BusyBox router persona on Telnet. Every scenario connects from its own source address (127.20.N.1) so alerts, events and reports can be attributed to it.

Reading the table: "Alert" means a Telegram message was sent, "AbuseIPDB" means the source address was reported. Rows with no alert are intended: scanners and credential guesses are logged (JSONL) but never reach Telegram. Two or more login attempts are still reported to AbuseIPDB as Brute-Force (category 18). The `/.env` row alerts on the path heuristic alone (enabled on the ADB/TR-069 ports only, never on the camera personas); it is deliberately **not** sent to AbuseIPDB because a bare path is weaker evidence than a request body. A SOAP request to the TR-064 endpoint counts as body evidence and is reported.

## What this simulation does not prove

- It replays attack patterns taken from public reports; it cannot show what real botnets will send next. A new exploit family needs a new scenario.
- Traffic comes from loopback addresses, so GeoIP/ASN enrichment, the public-IP check in the AbuseIPDB reporter (disabled for this run only) and real network latency are not exercised.
- Telegram and AbuseIPDB are local fakes. Their documented request formats are checked, but real rate limits, outages and account policies are not.
- The Docker image, compose file and `install.sh` are not part of this test; they need a run on the VPS.
- Payloads are harmless ELF-looking bytes and are only stored, never executed.
